### correctness

- **G-corr-1** `LeanMlir/Proofs/Codegen/StableHLO/Basic.lean:746` (`SHlo.biasGradB`), `:2200` (den arm), `:740-744` (comment) — `biasGradB : SHlo (N*n) → SHlo (N*n)` has `den = den e`, the identity. The text it prints (`skel` → `.biasGrad n`, Pretty.lean:2011-2014) is `reduce … across dimensions = [0] → tensor<n>`. So its index and its `den` both disagree with the printed op, and the batch sum is left to trusted text. The comment at :740-744 says `weightGradB`/`biasGradB` "denote the same thing" as `denseWeightGradB`/`denseBiasGradB`. That holds for `weightGradB` (a Σ over `Fin N`) and is false for `biasGradB`. Every consumer states the missing Σ outside the node: `GradNodesB.headBGradB_den` (Foundation/GradNodesB.lean:618), `ViTParamGrad:1138/1181`, `ConvNeXtParamGrad:547/594`, `ViTStepTieGB:276/287`, `ConvNeXtStepTieGB:285/302`, and the carve-out prose in `ViTFoldGB:35-54` and `ConvNeXtFoldGB:25-48`. **Fix:** change the type to `biasGradB {N n} : SHlo (N*n) → SHlo n` and the arm to `fun j => ∑ k : Fin N, batchSlice N n (den e) k j` (`denseBiasGradB`'s arm verbatim). Keep `skel … => .biasGrad n (skel e)`, so the text is unchanged. Restate `headBGradB_den` at the summed node and drop the external Σ from the four ParamGrad/StepTie sites and the carve-out prose. Correct the :740-744 comment to name only `weightGradB`. The per-example `biasGrad : SHlo n → SHlo n` stays: at one example the identity is right. **Evidence:** den arms at Basic:2200 vs `denseBiasGradB` at Basic:1902; emit arm at Pretty:2011; call sites ViTRenderB:526, ConvNeXtRenderB:554. **Cost:** root-file edit (Basic.lean rebuilds most of `Certs`); 1 AuditAxioms pin (`headBGradB_den`, name kept); no tex/yaml/comparator hits (`grep 'biasGradB (N' tests/comparator blueprint formalization.yaml` is empty); about ±40 lines. **Gate:** `lake build Certs CertsHeavy`, AuditAxioms, byte-identical artifacts. **Size:** M.

- **G-corr-2** Every batched renderer's loss cotangent: `ResNet34RenderB.lean:~1320-1333`, `ResNet50RenderB.lean:~790-804`, `MobileNetV2RenderB.lean:~690-700`, `MobileNetV4RenderB.lean:~958-968`, `EfficientNetRender/Basic.lean:~946-956`, `ConvNeXtRenderB.lean:~535-545`, `ViTRenderB.lean:~505-517`. Each capstone T3 tie starts from a named graph: `Foundation/SmoothedLossCot.smoothedLossCotGraph`, `…GraphDiv` for ConvNeXt/ViT, and `BceLossCot.bceLossCotGraph` for R50's BCE path. The renderers do not print that graph. Each emits the six nodes (`softmaxRow|expe∘softmaxDiv → subB → scaleB → addVB → shiftB → divConstB`) as six separate `pretty` calls, and no `#guard` compares that text with `pretty` of the graph (`grep -rn smoothedLossCotGraph tests LeanMlir/Proofs/Codegen` finds only AuditAxioms and comparator lines). This is the gap `FwdGraphTextTies` closed for the forward blocks, left open at the top of every backward. The numeric `*-adam-tie` gates check the arithmetic, not that the capstone's graph is the printed one. **Fix:** give the graphs a computable twin that takes the shift constant as an ℝ argument (the `-(α/K)` division is what makes `smoothedLossCotGraph` `noncomputable`). For example `smoothedLossCotGraphAt N K (α s B) …`, with `smoothedLossCotGraph := …At … (-(α/K)) …` and `_den` / `_row` unchanged. Then either (a) have a RenderKit helper `smoothedCotB` print `pretty B (smoothedLossCotGraphAt …)` and call it from the seven renderers, which is text-identical because postorder and `fresh` order match the six-call sequence, or (b) add `#guard`s in `FwdGraphTextTies` comparing each renderer's cotangent text with `prettyText B (…At …)`. **Cost:** Foundation/SmoothedLossCot + BceLossCot (+2 defs), 7 renderers; about −80 lines with (a). **Gate:** byte-identical artifacts, `lake build Certs`. **Size:** M.

- **G-corr-3** `FwdGraphTextTies.lean:35-37` ("Not covered: ConvNeXt-T and ViT") and `ViTRender.lean:155-165` (`vBlockFwd` "Mirrors `vitBlockGraphMHV` node-by-node"). The T2 theorems `vitFwdGraphKMHV_faithful` and `convNextFwdGraphTCh_faithful` are stated at `vitBlockGraphMHV` / `convNextFwdGraphTCh`. The per-example emitters (`vBlockFwd`, `vlnFwd`, ConvNeXtRender's block/`headLnFwdSite`) re-spell those graphs node by node, and the only link is reading. `tests/TestViTTrainPC.lean` and `TestConvNeXtTTrainPC.lean` are a third node-by-node copy, not `pretty` of the graph. The chain is T2 graph ↔ per-example emitter (unguarded) ↔ committed bytes (`vit-fwd-b-tie` / `convnext-fwd-b-tie`). The book still says "`vitFwdGraphKMHV` denotes `vitForwardKV`: the rendered ViT is the tower above" (`blueprint/src/content.tex:12046-12048`). Both graphs are computable `def`s (ViTMultiHead.lean:197, ConvNeXtFullT.lean:524), so a text guard is possible, and the "per-example with their own constructors" reason does not apply: the per-example emitters use those same constructors. **Fix:** make `vBlockFwd` / the ConvNeXt block emitter public (they are `private`), then add per-block `#guard`s in `FwdGraphTextTies` (block, stem/patch-embed, head) against `prettyText bs (vitBlockGraphMHV … (leaf …))` and the ConvNeXt block graph, and update the module docstring's coverage line. **Cost:** two `private` → public, about +40 guard lines, one extra import. **Gate:** `lake build` of the guard module. **Size:** M.

- **G-corr-4** `StableHLO/Pretty.lean:1797` (`.flatConvStride4F`, pad `(k−1)/2 − 1`), `:1811-1815` (`.flatConvStridedXlaF`, pad `[p−1, p]`), the batched `"convStridedXla*"`, `"depthwiseStridedXla*"` and `"convStride4P*"` arms, and `Basic.lean:~98-115` (`BatchableOp.convStridedXla` comment). The pad formulas agree with `den` only on an unstated kernel-size domain. With Nat subtraction, at `kH ∈ {1, 2}` the XLA-SAME stride-2 arms emit pad `(0,0)` and read `x[2i+kh]`, while `den = decimateOddFlat ∘ flatConv` reads `x[2i+1+kh−p]`. The stride-4 arm at `kH ∈ {1, 2}` likewise reads `x[4i+kh]` against `den`'s `x[4i+1+kh−p]`. These texts are well-typed, so they parse, run, and compute a different function from the `den` every theorem is about. At `k = 1` the emitted text is what XLA SAME actually does, so it is `flatConvStride2Xla`'s claim "= XLA SAME at an even input" (`Architectures/StridedConv.lean:~330-340`, "verified … k ∈ {3,5,7}") that fails there. Even `k ≥ 4` on the XLA arms and even `k` on the stride-1 symmetric arms (`emitFlatConv`, `.convBack`, `.convWeightGrad*`, pad `(p,p)`) change the output shape, so they fail loudly. No shipped artifact is affected: every XLA site is 3×3 or 5×5 and every stride-4 site is 4×4 (grep `StridedXla` in the renderers). The domain is latent and unstated, and the constructors accept any `kH kW`. **Fix:** have those `emitTok` arms return the `// MALFORMED …` fallback when the kernel is outside the faithful domain: odd `k ≥ 3` for the XLA arms, `k ≥ 3` for stride-4, odd `k` for the symmetric stride-1 arms. `regen_verified_mlir.sh`'s silent-emit audit already fails on that marker, so this is byte-identical for every shipped shape. State the domain in the constructor comments and in `flatConvStride2Xla`'s docstring. **Cost:** about 15 lines in Pretty. **Gate:** byte-identical artifacts. **Size:** S.

### api-design

- **G-api-1** There are two optimizer selectors with two dispatch tails. `StableHLO.OptKind {adamw, rmsprop}` (Pretty.lean:4575) drives RenderKit's `adamOne`/`rmsOne`/`adamOneEma` (MNv2, B0, ConvNeXt, ViT). `R34Opt {adamw, heavyBall, sgd, lamb, adamwAccum k, lambAccum k}` (ResNet34RenderB.lean:395) drives `optOne`/`optAllParams`/`optConstsB` (R34, R50, MNv4). The `.adamw` case exists in both, and the EMA shadow is spelled `%{nm}e` in `adamOneEma` against `%{nm}ema` in `optOne`, a real collision workaround documented at RenderKit:~130. Choosing an optimizer for a net means knowing which family its renderer belongs to, and adding RMSProp to R34, or LAMB to MNv2, means writing a third tail. **Fix:** one `OptRecipe` enum with the union of the cases (and `emaSuf` as a parameter, the way `packedTrainSig` already takes it), plus one `optOne` in RenderKit. `adamOne`, `rmsOne` and `adamOneEma` become its arms. (carried: planning/audit_v2.md §5 "per-param optimizer step ×7 … → `optOne` + `.rmsprop` arm + `emaSuffix` param, in RenderKit". The RenderKit commit recorded "R34's multi-optimizer `optOne` stays" and gave no reason.) **Cost:** `R34Opt` appears in 12 `.lean` files, including `apps/ablation/MainResnet34Ablation.lean`, `LeanMlir/Verified/{NetsCore,Train}.lean`, and `tests/Test{MomTie,OptStepFixtures,VariantPredicates,R34TrainB2,…}`; no tex/yaml pins. **Gate:** byte-identical artifacts. **Size:** M.

### naming

- **G-name-1** 33 String-valued renderers are named `…Faithful{V,B,}`. Examples: `resnet34AdamTrainStepFaithfulB`, `mnv4FwdFaithfulV`, `vitAdamTrainStepFaithful`, `convNextTrainStepFaithfulV` (list: `grep -rhoE 'def [a-z][A-Za-z0-9]*Faithful[A-Za-z0-9]*' LeanMlir/Proofs/Codegen`). The word "Faithful" advertises a proven property on a function that returns text. Every `*_faithful` theorem in the same namespace is the actual claim, so `mnv2FwdEvalFaithfulV` (a `String`) sits next to `mobilenetv2FwdGraphBFull_faithful` (a theorem). The suffix carries no information either. `mnv4FwdFaithfulV` and `efficientnetFwdFaithfulV` render the batched chains (`mnv4FwdChainB`, `enetFwdChain` at `N := B`), exactly like `mobilenetv2FwdFaithfulB` and `resnet34FwdFaithfulB`. **Fix:** rename to `…Render` / `…Text` with one meaning for any suffix kept, for example `resnet34AdamTrainStepText`, `mnv4FwdText`, `vitAdamTrainStepText`. **Cost:** pins are cheap. Each name has 3–6 `.lean` hits (the renderer, its `*Artifacts` writer, 1–3 tests) and 0 hits in tex/yaml/scripts/.github (checked for four representative names). **Gate:** byte-identical artifacts, `check_target_names.sh`, `name_lint.py`. **Size:** M (mechanical, 33 names).

### documentation
