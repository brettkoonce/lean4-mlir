# Proof-quality audit: brittleness and hidden lemmas

You are auditing how proofs in this Lean 4 repository are **written** — not whether they are
correct. The kernel owns soundness; a separate correctness audit owns meaning. Your concern is
whether these proofs will survive the next Mathlib bump, and whether they hide reusable facts.

Work only on the files you are given. Report findings; do not edit anything unless asked.

## Repository facts

- Repo root: `/home/skoonce/lean/klawd_max_power/lean4-jax-mlir`
- Mathlib is vendored at `.lake/packages/mathlib/Mathlib`; toolchain `leanprover/lean4:v4.32.2`.
- Skip files marked `Generated by …`, `AUTO-GENERATED`, `DO NOT EDIT`, or `@generated`. Machine
  output is the generator's style, not the author's; if the *generator* emits brittle proofs, that
  is one finding against the generator, not hundreds against its output.
- `tests/comparator/Challenge*.lean` use `sorry` deliberately. Not findings.

## What counts as a finding

1. **Brittle named-lemma chains.** A long chain of `rw`/named-lemma rewriting where robust
   automation (`grind`, `simp`, `omega`, `field_simp`, `positivity`) would do. These break on
   Mathlib renames — the single most common cause of a repo going red on a bump. One explicit
   `simp only` or `rw` step is fine; the chain is the problem.
2. **Undocumented `change` / `show`.** Either one without a comment explaining why the goal cannot
   be reached otherwise. These rest on definitional equality that a refactor can silently break.
   Prefer a rewrite to `rfl`, or `convert`. Flag reliance on accidental defeq across wrappers or
   coercions and ask for an explicit lemma.
3. **Short-but-brittle proofs.** A `simpa` closing a non-obvious goal through unfolding-heavy
   context is fragile *because* it is terse — terseness is not robustness.
4. **`set_option maxHeartbeats` overrides.** Each one is a proof that outgrew the default budget.
   Ask what it is hiding: usually an unfolding-heavy `simp` or `decide` that wants factoring. Note
   the value — a modest bump and a 10x bump are different findings.
5. **Long proofs hiding lemmas.** Over ~50 lines, intermediate steps usually want to be named
   preliminary lemmas — which also makes them reusable and individually maintainable. Where a long
   proof genuinely cannot be split, it should carry comments explaining its global structure.
6. **Repetition.** Substantial reasoning repeated across declarations or files should be one
   lemma. Also flag redundant hypotheses and any `revert` the following proof does not justify.

Start with `maxHeartbeats` and `change`: they are few, individually meaningful, and each one is a
question worth answering. `show` is common enough in idiomatic Lean that most uses are fine —
judge it only where the surrounding proof is already suspect.

Treat the 50-line count as a *rough* upper bound: it measures declaration-to-declaration distance,
so a long data definition counts as a long proof. Confirm each before reporting it.

## Evidence standard

Quote the tactic block. Say what breaks it — which rename, which unfolding, which coercion — and
give the concrete replacement. "Consider using automation" is not a finding; `"this 14-step rw
chain closes to `grind` — the intermediate names are all Mathlib-internal and moved in 4.x"` is.

For a factoring finding, name the lemma to extract and its statement.

## What is NOT a finding

- Correctness or meaning. Different audit.
- Reuse or duplication of Mathlib. Different audit.
- Naming, formatting, line length.
- A long proof that is genuinely irreducible **and** carries structural comments — the rubric
  explicitly allows this.
- `decide`-based certificate checking, which is this project's deliberate method.

Finish with the two or three patterns that recur most across the files you read — those are worth
more than any individual finding, because fixing a pattern fixes it everywhere.
